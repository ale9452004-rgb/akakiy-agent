# Архитектурные решения (Architecture Decision Records)

Данный документ фиксирует ключевые архитектурные решения, принятые в процессе проектирования и разработки ассистента **«Акакий»**, их контекст, обоснование и последствия.

---

## ADR-001: Локальный LLM-бэкенд на базе Ollama (`qwen3:8b`)

* **Статус**: Принято
* **Контекст**:
  Акакий проектируется как полностью локальный персональный ассистент, способный работать без подключения к интернету, без передачи исходного кода проекта, персональных заметок и конфиденциальных данных во внешние облачные API (OpenAI, Anthropic и др.).
* **Решение**:
  Использовать локальный сервер Ollama (`http://localhost:11434`), работающий на машине пользователя. В качестве основной рабочей модели выбрана `qwen3:8b`, обладающая сильной поддержкой русского языка, логики планирования и нативного вызова инструментов (Native Tool Calling через спецификацию `tools`).
* **Последствия**:
  * **Плюсы**: Полная автономность, нулевая стоимость API-токенов, абсолютная конфиденциальность кода и личных данных.
  * **Минусы**: Зависимость времени отклика от характеристик локального CPU/GPU; необходимость оптимизации количества LLM-обращений.

## ADR-002: Двухуровневая маршрутизация (Deterministic Fast-Path + Native Tool Calling)

* **Статус**: Принято
* **Контекст**:
  При передаче любого пользовательского запроса (включая тривиальные «создай задачу купить хлеб», «покажи задачи», «покажи файлы») в LLM модель на CPU генерирует 2 последовательных запроса (выбор инструмента + итоговый ответ), что занимало 10–15 секунд на каждое действие.
* **Решение**:
  Внедрить в `Agent.choose_tool()` детерминированный fast-path на базе предсказуемых регулярных выражений для очевидных CLI- и бытовых команд (задачи, заметки, списки, напоминания, память, поиск файлов). При совпадении инструмент вызывается мгновенно. Запросы на естественном языке, вопросы и сложные инструкции передаются в Native Tool Calling Ollama.
* **Последствия**:
  * **Плюсы**: Время отклика на типовые команды сократилось с 13.5 секунд до 0.05–1.09 миллисекунд (>10 000x ускорение), экономия ресурсов процессора.
  * **Минусы**: Необходимость поддерживать актуальность регулярных выражений при добавлении новых типовых команд.

## ADR-003: Единый ContextManager как источник истины

* **Статус**: Принято
* **Контекст**:
  На ранних этапах история сообщений велась независимо в `OllamaClient`, а контекст инструментов накапливался в `Agent`. Это приводило к рассинхронизации, риску переполнения контекстного окна и уязвимости к prompt injection при передаче фактов памяти.
* **Решение**:
  Создать класс `ContextManager` (`tools/context.py`) как единственный источник истины о ходе текущей беседы. `ContextManager`:
  1. Реализует скользящее окно ходов диалога (`max_turns=10`) с корректным сохранением пар `tool_call` / `tool_result`.
  2. Реализует Prompt Injection Shield: системный промпт остаётся неизменяемым, а пользовательские факты памяти передаются как справочные блоки данных.
  3. Динамически извлекает только релевантные факты долговременной памяти по ключевым словам запроса.
* **Последствия**:
  * **Плюсы**: Защита от переполнения контекста, защита от подмены инструкций через память, детерминированная сборка промпта.
  * **Минусы**: Требует синхронизации состояния при вызовах через различные интерфейсы.

## ADR-004: Изоляция хранилища `data/` и атомарная запись

* **Статус**: Принято
* **Контекст**:
  Файлы долговременной памяти (`memory.json`) и бытовых сущностей (`household.json`) содержат приватные данные пользователя и не должны попадать в публичный Git-репозиторий. При внезапном прерывании процесса (Ctrl+C, сбой питания) прямая запись в JSON грозила повреждением структуры файла.
* **Решение**:
  1. Вынести все локальные хранилища в директорию `data/`, внесённую в `.gitignore`.
  2. Реализовать атомарную запись во всех менеджерах данных (`MemoryManager`, `HouseholdManager`): сериализация сначала пишется во временный файл (`.tmp`), затем атомарно заменяет целевой файл через системный вызов `os.replace`.
  3. Защитить доступ к данным рекурсивными мьютексами (`threading.RLock`).
* **Последствия**:
  * **Плюсы**: Гарантия целостности данных при падениях процесса, отсутствие race condition при одновременных запросах из UI и Voice, изоляция от git-коммитов.
  * **Минусы**: Небольшой оверхед на дисковые операции записи временных файлов (нивелируется малым размером JSON).

## ADR-005: Модульная архитектура навыков (`skills/`) без дублирования ядра

* **Статус**: Принято
* **Контекст**:
  При росте числа инструментов (разработка, память, задачи, списки, напоминания — более 20 инструментов) передача полной схемы всех инструментов в каждый LLM-запрос снижала качество работы модели `qwen3:8b`, вызывала галлюцинации и превышала оптимальный размер промпта.
* **Решение**:
  Ввести слой навыков (`skills/`) под управлением `SkillRegistry`. Навыки (`ProjectSkill`, `MemorySkill`, `HouseholdSkill`):
  1. Классифицируют запрос по регулярным выражениям.
  2. Предоставляют специализированную системную инструкцию.
  3. Ограничивают список передаваемых модели инструментов только релевантным подмножеством (`scoped_tools`).
  4. **Строгий запрет**: Навыки не имеют собственных экземпляров LLM-клиента, Агента или истории, а работают исключительно поверх существующего `Agent`.
* **Последствия**:
  * **Плюсы**: Модель видит только нужные инструменты, снизилось число галлюцинаций, промпт стал компактнее.
  * **Минусы**: При нечётких запросах на стыке навыков требуется fallback на полный набор инструментов.

## ADR-006: Локальный автономный голосовой конвейер (Vosk + pyttsx3)

* **Статус**: Принято
* **Контекст**:
  Голосовой интерфейс должен быть полностью локальным (без внешних ключей и API), быстрым, отзывчивым и поддерживать непрерывный диалог (Continuous Voice UX).
* **Решение**:
  1. **STT**: Локальный Vosk с компактной моделью `vosk-model-small-ru-0.22`.
  2. **Адаптивный порог тишины (Adaptive Endpointing)**: Динамическая калибровка фонового шума микрофона в первые фреймы (`speech_threshold = max(0.042, min(0.08, avg_noise * 1.55))`). Устранена проблема зависания на 10–15 секунд при фоновом аппаратном шуме.
  3. **Wake Word «Акакий»**: Пост-обработка `correct_recognized_text` нормализует искажения Vosk (`«а какие»`, `«а как и»` $\to$ `«акакий»`), сохраняет имя в логах и GUI, а функция `strip_wake_word` отсекает обращение перед передачей в агент.
  4. **TTS**: `pyttsx3` (Windows SAPI5) в фоновом потоке с очередью и возможностью немедленного прерывания по кнопке «Стоп» или голосовой команде выхода («хватит», «отключись»).
  5. **Безопасность ответов**: Ошибки (`success=False`) строго озвучиваются как ошибки и никогда не выдаются за успешные операции.
* **Последствия**:
  * **Плюсы**: Полная независимость от интернета, нулевая задержка сети, отсутствие платных API.
  * **Минусы**: Роботизированный тембр SAPI5 по сравнению с нейросетевыми облачными TTS; Vosk small требует акустических замен частых технических терминов.

## ADR-007: Десктопный интерфейс GUI 2.0 на Tkinter с процедурным Neural Core

* **Статус**: Принято
* **Контекст**:
  Требовался полноценный десктопный хаб для управления всеми функциями Акакия (чат, задачи, заметки, напоминания, списки, память, настройки), наглядной индикации состояний и громкости голоса, не утяжеляющий проект тяжеловесными веб-фреймворками (Electron, PyQt, Webview).
* **Решение**:
  1. Реализовать интерфейс на встроенной библиотеке `tkinter` с фиксированной сеткой 1920x1280 (Topbar, Sidebar, Main Workspace, Command Bar).
  2. Использовать процедурную 3D-проекцию математической нейросферы (`NeuralCore`) на стандартном `tk.Canvas` с реакцией на RMS микрофона и смену состояний (`idle`, `thinking`, `working`, `listening`, `speaking`, `error`).
  3. Обеспечить потокобезопасность через `queue.Queue` и периодический опрос `_poll_queue`.
  4. Сохранять историю чата и состояние ввода при переключении между разделами.
* **Последствия**:
  * **Плюсы**: Нулевые внешние зависимости, мгновенный запуск, нативная работа в Windows, низкое потребление памяти (< 100 МБ).
  * **Минусы**: Ограниченные возможности нативной стилизации Tkinter (компенсировано кастомными отрисованными компонентами и плоской тёмной палитрой).

## ADR-008: Политика безопасности деструктивных действий (`requires_confirmation`)

* **Статус**: Принято
* **Контекст**:
  Ассистент обладает доступом к изменению и удалению файлов, запуску системных терминальных команд, выполнению коммитов и удалению пользовательских заметок/задач. Случайное или галлюцинированное выполнение деструктивной команды недопустимо.
* **Решение**:
  Все потенциально опасные инструменты (`delete_task`, `delete_note`, `delete_reminder`, `delete_list`, `write_file`, `edit_file`, `git_commit`, `git_push`, `run_command`) помечены в `tools/registry.py` флагом `requires_confirmation = True`. Функция `dispatch()` перехватывает их вызов и запрашивает явное подтверждение пользователя через интерактивный консольный диалог или модальное окно в GUI.
* **Последствия**:
  * **Плюсы**: Исключена случайная потеря пользовательских данных и повреждение кодовой базы.
  * **Минусы**: Требует одного дополнительного действия пользователя для подтверждения удаления или перезаписи.

## ADR-009: Выделение детерминированной маршрутизации в `CommandRouter` (Этап R2)

* **Статус**: Принято
* **Контекст**:
  Модуль `tools/agent.py` превышал 1050 строк кода и сочетал в себе оркестрацию жизненного цикла запроса, многошаговый LLM-цикл Native Tool Calling, низкоуровневые регулярные выражения синтаксического разбора команд в `choose_tool()`, строковые проверки планов и прямое дублирование регулярных выражений команд памяти в `process()`. Это приводило к скрытому затенению команд и затрудняло расширение правил маршрутизации.
* **Решение**:
  Создан независимый модуль [tools/router.py](file:///c:/Akakiy%20agent/tools/router.py) с классом `CommandRouter`. В него вынесены:
  1. Синтаксические регулярные выражения и наборы точных фраз для CLI-команд проекта (`find_file`, `list_files`, `search_files`).
  2. Детерминированный разбор бытовых операций (`Tasks`, `Notes`, `Reminders`, `Lists`).
  3. Единые правила разбора команд памяти (`remember`, `recall`, `forget`, `search`, `clear`), исключающие дублирование между fast-path и оркестратором.
  4. Распознавание команд управления планами (`create`, `execute`, `get`, `clear`).
  Метод `Agent.choose_tool()` сохранён как прозрачный фасад к `router.choose_tool()`, а `Agent.process()` трансформирован в чистый оркестратор: `CommandRouter (fast-path) -> TeamworkCoordinator -> SkillRegistry -> Ollama Native Tool Calling`.
* **Последствия**:
  * **Плюсы**: `tools/agent.py` сократился на ~350 строк; устранены дублирования и затенения команд памяти; задержка детерминированного роутинга составляет < 0.05 мс; 100% обратная совместимость со всеми существующими контрактами и тестами.
  * **Минусы**: Появился один дополнительный легковесный модуль без внешних зависимостей.

## ADR-010: Модуляризация представлений GUI в `ui/views/` (Этап R3)

* **Статус**: Принято
* **Контекст**:
  Модуль `gui.py` превышал 1600 строк кода и объединял обязанности общесистемного каркаса (Desktop Shell: Topbar, Sidebar, Command Bar, асинхронная очередь `queue.Queue`, интеграция с `VoiceService`, управление состояниями `NeuralCore`) и детальную реализацию всех 8 пользовательских экранов с их виджетами и CRUD-обработчиками. Это затрудняло поддержку UI, усложняло модульное тестирование и нарушало принцип единственной ответственности (SRP).
* **Решение**:
  1. Создать пакет [ui/views/](file:///c:/Akakiy%20agent/ui/views/) с базовым классом `BaseView(tk.Frame)` ([ui/views/base.py](file:///c:/Akakiy%20agent/ui/views/base.py)), фиксирующим единый контракт (`render()`, `refresh()`, доступ к Shell и единым сервисам без дублирования состояния, общие темы оформления).
  2. Последовательно вынести все экраны в изолированные модули:
     * Бытовые экраны: `TasksView` (`tasks.py`), `RemindersView` (`reminders.py`), `NotesView` (`notes.py`), `ListsView` (`lists.py`).
     * Служебные экраны: `MemoryView` (`memory.py`), `SettingsView` (`settings.py`).
     * Центральные экраны: `HomeView` (`home.py`), `ChatView` (`chat.py`).
  3. Сохранить в `AkakiyGUI` 100% обратную совместимость через делегирующие методы (`_ui_*`, `_append_*`, `_insert_*`, `_quick_complete_task`) и свойства-прокси (`entry_*`, `chat_text`, `log_text`, `tasks_list_frame`, `lbl_val_res` и др.).
  4. Обновить метод `refresh_current_view()` для реактивного обновления активного экрана через соответствующий метод `view.refresh()`.
* **Последствия**:
  * **Плюсы**: `gui.py` разгружен на более чем 500 строк кода и остался чистым оркестратором Shell; экраны стали независимо тестируемыми; визуальный стиль, геометрия и пользовательский опыт остались на 100% идентичными; тесты покрывают как изолированные представления, так и сквозную интеграцию с Shell.
  * **Минусы**: Необходимость поддерживать прокси-свойства в Shell для обратной совместимости внешних вызовов.

## ADR-011: Модульная система уведомлений (ReminderMonitor → NotificationService → NotificationWindow)

* **Статус**: Принято
* **Контекст**:
  Требовалось реализовать реактивное фоновое оповещение пользователя о наступивших напоминаниях в десктопном интерфейсе Акакия с возможностью выполнения (`✓ Выполнено`), откладывания (`⏰ Отложить`) и закрытия (`×`), не допуская загромождения главного модуля `gui.py` шедулерами и вспомогательными окнами, а также обеспечив расширяемость системы для любых будущих типов уведомлений (системные алерты, завершение фоновых задач и др.).
* **Решение**:
  1. Разделить систему на три изолированных уровня ответственности:
     * `ReminderMonitor` ([notifications/monitor.py](file:///c:/Akakiy%20agent/notifications/monitor.py)): фоновый поток-демон, опрашивающий `HouseholdManager.check_due_reminders()`, свободный от зависимостей от Tkinter, с дедупликацией наступивших событий (`_notified_ids`).
     * `NotificationService` ([notifications/service.py](file:///c:/Akakiy%20agent/notifications/service.py)): сервис управления стеком окон на главном UI-потоке с автоматическим расчетом экранных координат в правом нижнем углу и репозиционированием оставшихся уведомлений при закрытии любого из них.
     * `NotificationWindow` ([notifications/window.py](file:///c:/Akakiy%20agent/notifications/window.py)): компактное модульное окно `tk.Toplevel` (`overrideredirect(True)`, `attributes("-topmost", True)`) в фирменной темной теме с поддержкой бейджей типов и кнопок действий.
  2. `AkakiyGUI` выступает только связующим звеном, передающим события через потокобезопасную очередь `queue.Queue`.
  3. Отказаться от использования сторонних библиотек (Windows Toast) и аудиосигналов в пользу чистой локальной реализации на Tkinter.
* **Последствия**:
  * **Плюсы**: Четкое разделение ответственности (SRP); возможность многократного использования `NotificationService` для любых событий ассистента; 100% потокобезопасность (`RLock` + `master.after`); независимая тестируемость каждого компонента.
  * **Минусы**: Необходимость явного закрытия активных окон и остановки фонового монитора при завершении приложения (`_on_window_close`).
