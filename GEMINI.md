## 👥 Терминология и разделение ролей

* **ИИ-ассистент (Antigravity/Gemini)** — внешний разработчик (ИИ в среде разработки), который исследует репозиторий, проектирует решения, редактирует код и запускает проверки.
* **Акакий / Agent** — разрабатываемое приложение (локальный персональный ассистент), его архитектура, исполняемый код и внутренние классы (`Agent`, `ContextManager`, `HouseholdManager`, `VoiceService`, `GUI` и инструменты).

## Уровень 1. 🧠 Инженерная дисциплина (Правила разработки)

1. **Анализ перед действием**: Всегда сначала исследуй существующий код, зависимости и структуру на диске перед внесением любых изменений. Источник истины — только диск.
2. **Сохранение архитектуры**: Не меняй архитектуру, устоявшиеся паттерны и структуру папок без предварительного согласования с пользователем.
3. **Запрет на необоснованные workaround**: Если текущая архитектура мешает корректно и чисто выполнить задачу, запрещено создавать необоснованные костыли и обходные пути. Опиши проблему и предложи вариант архитектурного изменения пользователю.
4. **Запрет на слепое переписывание**: Не переписывай рабочий код и файлы целиком без прямой необходимости.
5. **Минимальные точечные правки**: Всегда отдавай предпочтение локальным, минимальным и хирургически точным изменениям (через точечный edit/replace, а не полную перезапись файла).
6. **Ограничение области задачи (Scope Boundary)**:
   * Решай строго поставленную задачу; не проводи попутный или скрытый рефакторинг.
   * Не исправляй автоматически обнаруженные сторонние проблемы, не относящиеся к текущей задаче.
   * Все найденные сторонние дефекты и возможности для оптимизации выноси отдельным списком в итоговый отчёт для обсуждения с пользователем.
7. **Проверка зависимостей**: Перед изменением любого файла или сигнатуры функции проверяй, где и как они используются в других модулях проекта.
8. **Обязательная валидация**: После каждого изменения кода проверяй синтаксис и работоспособность (запуск `validate_project`, `python -m py_compile` или тестов).
9. **Критерий завершённости**: Не считай задачу выполненной только потому, что файл был отредактирован. Задача считается завершённой только после фактической проверки результата.
10. **Без дубликатов и потери функциональности**: Не создавай дублирующие классы, функции или файлы-клоны. Не удаляй существующую функциональность и параметры, если пользователь прямо об этом не просил.
11. **Актуализация проектной документации**:
    * После каждой завершённой задачи проверяй, затронуты ли архитектура, важное решение или статус проекта:
      * Если затронута архитектура (структура модулей, интерфейсы, потоки данных) — точечно обнови [ARCHITECTURE.md](file:///c:/Akakiy%20agent/ARCHITECTURE.md).
      * Если принято новое архитектурное решение (ADR) или изменён устоявшийся подход — зафиксируй в [DECISIONS.md](file:///c:/Akakiy%20agent/DECISIONS.md).
      * Если изменился статус задач или завершён этап — обнови [TASKS.md](file:///c:/Akakiy%20agent/TASKS.md).
    * Если изменения не затронули архитектуру, решения и статус — **документацию не трогать**.
    * **Не делать отдельный этап исследования ради документации**.

## Уровень 2. 🤖 Мета-правила поведения ИИ-ассистента (Самоконтроль)

### 1. Рабочий цикл разработки: RESEARCH → PLAN → IMPLEMENT → VERIFY
Любая задача выполняется последовательно по четырём фазам:
1. **RESEARCH (Исследование)**:
   * Изучи фактическое состояние файлов на диске, затрагиваемые модули, места вызовов и зависимости.
   * Источник истины — только диск. Никогда не полагайся на память предыдущих диалогов или устаревшие описания.
2. **PLAN (Планирование)**:
   * Для нетривиальных задач перед внесением изменений определи список файлов, конкретные функции и суть планируемых правок до начала реализации.
   * Для простых локальных задач этот этап может быть кратким и объединён с фазой RESEARCH.
3. **IMPLEMENT (Реализация)**:
   * Внеси минимальные точечные изменения строго в рамках согласованного плана.
   * Не затрагивай несвязанный код и не делай попутных изменений.
4. **VERIFY (Проверка)**:
   * Проверь синтаксис (через `python -m py_compile` или вызов валидации), тесты и фактический результат.
   * Никогда не объявляй задачу выполненной без прохождения этой фазы.

### 2. Матрица автономности ИИ-ассистента
* 🟢 **Автономно (Действуй самостоятельно)**:
  Чтение файлов, поиск по проекту, статический анализ, проверка синтаксиса, запуск тестов, исполнение консольных команд для исследования и верификации, локальные точечные исправления строго в рамках поставленной задачи, точечное обновление документации по правилу 11, выполнение регламентированного Git Workflow после успешного VERIFY.
* 🟡 **Объяснить и выполнить (Сначала кратко поясни намерение)**:
  Изменение публичных сигнатур функций, изменение формата возвращаемых контрактов, правки в нескольких взаимосвязанных модулях, нетривиальный рефакторинг в границах задачи.
* 🔴 **Остановиться и спросить (Требует явного одобрения пользователя)**:
  Архитектурные изменения, удаление файлов/классов, удаление существующей функциональности, деструктивные операции Git (reset/clean/restore с риском потери кода), потенциально опасные или разрушительные системные команды.

### 3. Регламент работы с Git

#### Git Workflow
* После каждого завершённого логического этапа, если реализация прошла VERIFY и тесты успешны, автоматически выполнять `git status` → `git diff` → `git add` только изменённых файлов → `git commit` → `git push`.
* Commit должен содержать краткое описание завершённого этапа.
* Не выполнять commit/push для незавершённой работы, промежуточного состояния или при проваленных тестах.
* Перед commit проверить, что в изменениях нет секретов, `.env`, токенов и случайных временных файлов.
* Не включать в commit файлы из других незавершённых задач.
* После успешного push зафиксировать в отчёте commit hash и краткое описание версии.
* Git history использовать как точки восстановления между логическими этапами проекта.
* `git add`, `git commit` и `git push` в рамках этого workflow разрешены без дополнительного подтверждения пользователя, если все условия выше выполнены.

#### Общие правила и безопасность Git
* **Read-only операции (разрешены для анализа и проверки)**:
  Команды `git status`, `git diff`, `git log` разрешено выполнять автономно для проверки состояния рабочей копии, контроля диффов и формирования отчётов.
* **Деструктивные операции (строго по прямому указанию пользователя)**:
  Команды `git reset --hard`, `git checkout -f`, `git clean -fd` и любые другие операции с риском потери незафиксированного кода выполняются **исключительно по прямому указанию пользователя**.

### 4. Регламент выполнения консольных и терминальных команд
* **Разрешено автономно (без дополнительного согласования)**:
  Консольные команды, необходимые для исследования, разработки и проверки проекта, выполняются ассистентом самостоятельно:
  * Исполнение PowerShell-команд;
  * Запуск Python и скриптов в виртуальном окружении (`.\.venv\Scripts\python.exe`);
  * Синтаксическая компиляция (`py_compile`);
  * Запуск тестов, локальных проверок и отдельных вспомогательных скриптов;
  * Чтение файлов через консоль, поиск файлов и текстовых фрагментов;
  * Анализ структуры проекта;
  * Запуск команд, необходимых для проверки фактического поведения изменённого кода.
  > Не нужно каждый раз запрашивать разрешение на такие команды.

* **Ограничения и правила безопасности**:
  * **Scope команды**: консольные команды не должны использоваться для внесения изменений за пределами текущей задачи.
  * **Запрет на деструктивные действия**: запрещено выполнять потенциально опасные или разрушительные команды (`Remove-Item`, массовое удаление файлов, полная очистка проекта, правка системных настроек) без отдельного согласования.
  * **Оценка риска**: если команда может привести к потере данных или необратимому изменению проекта — остановись и запроси подтверждение.
  * **Приоритет правил Git**: консольные команды терминала не могут использоваться для обхода ограничений Git (`git commit`, `git push` и др. подчиняются разделу 3).

### 5. Регламент запуска тестов (Test Execution Policy)
* **Запрет на избыточный полный suite**: Не запускать полный test suite после каждого локального изменения.
* **Точечные проверки во время разработки**: Во время активной разработки запускать исключительно точечные тесты затронутой функциональности и проверку синтаксиса (`python -m py_compile`).
* **Обоснованность новых тестов**: Новые тесты добавлять только для новой логики или реально выявленных edge cases; запрещено создавать тесты ради механического увеличения количества.
* **Протокол завершения логического этапа**: После завершения реализации логического этапа строго последовательно выполнить:
  1. точечные тесты затронутых модулей;
  2. ровно один прогон полного test suite (`python -m unittest discover tests`);
  3. ровно один запуск валидации проекта (`validate_project()`).
* **Интеграционные и аппаратные тесты**: Интеграционные, GPU и внешние сервисные тесты запускать только в том случае, если изменённая функциональность действительно их затрагивает, и строго один раз в конце этапа.
* **Запрет на беспричинные повторы**: Не повторять уже успешно пройденный тест без изменения затронутого кода или диагностической необходимости.
* **Локализация сбоев перед правками**: При сбое теста сначала исследовать и определить точную причину ошибки; запрещено запускать полный suite для проверки каждой промежуточной правки.
* **Фиксация в отчёте**: В итоговом отчёте этапа обязательно указывать:
  * какие тесты запускались;
  * сколько новых тестов добавлено;
  * результаты финального полного suite и `validate_project()`.
