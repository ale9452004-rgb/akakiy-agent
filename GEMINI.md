# Регламент разработки и архитектурный контекст проекта «Акакий»

Данный документ является единым источником правил, архитектурного контекста и ограничений при работе в репозитории **«Акакий»**.

---

## 👥 Терминология и разделение ролей

* **ИИ-ассистент (Antigravity/Gemini)** — внешний разработчик (ИИ в среде разработки), который исследует репозиторий, проектирует решения, редактирует код и запускает проверки.
* **Акакий / Agent** — разрабатываемое приложение (локальный терминальный ассистент), его архитектура, исполняемый код и внутренние классы (`Agent`, `Planner`, `PlanExecutor` и инструменты).

---

## Уровень 1. 🧠 Инженерная дисциплина (Правила разработки)

1. **Анализ перед действием**: Всегда сначала исследуй существующий код, зависимости и структуру на диске перед внесением любых изменений.
2. **Сохранение архитектуры**: Не меняй архитектуру, устоявшиеся паттерны и структуру папок без предварительного согласования с пользователем.
3. **Запрет на необоснованные workaround**: Если текущая архитектура мешает корректно и чисто выполнить задачу, запрещено создавать необоснованные костыли и обходные пути. Опиши проблему и предложи вариант архитектурного изменения пользователю.
4. **Запрет на слепое переписывание**: Не переписывай рабочий код и файлы целиком без прямой необходимости.
5. **Минимальные точечные правки**: Всегда отдавай предпочтение локальным, минимальным и хирургически точным изменениям (через точечный edit/replace, а не полную перезапись файла).
6. **Ограничение области задачи (Scope Boundary)**:
   * Решай строго поставленную задачу; не проводи попутный или скрытый рефакторинг.
   * Не исправляй автоматически обнаруженные сторонние проблемы, не относящиеся к текущей задаче.
   * Все найденные сторонние дефекты и возможности для оптимизации выноси отдельным списком в итоговый отчёт для обсуждения с пользователем.
7. **Проверка зависимостей**: Перед изменением любого файла или сигнатуры функции проверяй, где и как они используются в других модулях проекта.
8. **Обязательная валидация**: После каждого изменения кода проверяй синтаксис и работоспособность (запуск `validate_project`, `python -m py_compile` или тестов).
9. **Критерий завершённости**: Не считай задачу выполненной только потому, что файл был отредактирован. Задача считается завершённой только после фактической проверки результата.
10. **Без дубликатов и потери функциональности**: Не создавай дублирующие классы, функции или файлы-клоны. Не удаляй существующую функциональность и параметры, если пользователь прямо об этом не просил.

## Уровень 2. 🏗️ Архитектура и специфика проекта «Акакий»

### Технический стек и окружение
* **Язык**: Python 3.
* **Окружение**: Виртуальное окружение в папке `.venv` (Windows PowerShell).
* **LLM-бэкенд**: Локальная Ollama (`http://localhost:11434/api/chat`), модель `qwen3:8b`.
* **Рабочая директория**: `C:\Akakiy agent`.

### Модули проекта и их фактическое состояние
* [main.py](file:///c:/Akakiy%20agent/main.py): Точка входа проекта. Запускает интерактивный консольный REPL-цикл (`while True`), считывает ввод пользователя, вызывает `Agent.process()`, форматирует и выводит результаты (шаги плана, логи инструментов, статус выполнения, обработку выхода).
* [commands.py](file:///c:/Akakiy%20agent/commands.py): Вспомогательный модуль быстрых команд (`show_status`, `show_files`, `read_file`).
  > [!NOTE]
  > **Фактическое состояние:** Файл существует и содержит функции `show_status`, `show_files`, `read_file`, но на данный момент **не подключён** к REPL-циклу [main.py](file:///c:/Akakiy%20agent/main.py).
* [ollama_client.py](file:///c:/Akakiy%20agent/ollama_client.py): Класс `OllamaClient` — обёртка над HTTP API Ollama. Управляет историей сообщений (`messages`), системным промптом Акакия и сетевыми таймаутами.
* [tools/agent.py](file:///c:/Akakiy%20agent/tools/agent.py): Класс `Agent` — мозговой центр Акакия. Классифицирует запросы (регулярные выражения + LLM), готовит изменения файлов (`prepare_edit`), делегирует планирование в `Planner` и исполнение в `PlanExecutor`.
  > [!NOTE]
  > **Фактическое состояние:** Сейчас система ориентирована на работу с инструментами и планами (tool/plan-oriented). Полноценный свободный разговорный чат без инструментов пока **не маршрутизируется** (запросы без инструментов возвращают ошибку распознавания).
* [tools/planner.py](file:///c:/Akakiy%20agent/tools/planner.py): Класс `Planner` — раскладывает многошаговые задачи пользователя на последовательность структурированных действий (JSON-план).
* [tools/plan_executor.py](file:///c:/Akakiy%20agent/tools/plan_executor.py): Класс `PlanExecutor` — пошагово запускает действия плана с валидацией и отслеживанием статусов.
* [tools/dispatcher.py](file:///c:/Akakiy%20agent/tools/dispatcher.py): Функция `dispatch` — маршрутизирует вызов инструмента по имени к зарегистрированной функции с проверкой флага подтверждения.
* [tools/registry.py](file:///c:/Akakiy%20agent/tools/registry.py): Реестр инструментов `TOOLS` (13 инструментов). Хранит ссылки на функции, описания инструментов и флаги подтверждения (`requires_confirmation`).
* [tools/files.py](file:///c:/Akakiy%20agent/tools/files.py): Инструменты файловой системы (`list_files`, `find_file`, `read_file`, `write_file`, `edit_file`, `search_files`).
* [tools/terminal.py](file:///c:/Akakiy%20agent/tools/terminal.py): Инструмент безопасного исполнения терминальных команд PowerShell (`run_command`).
* [tools/git.py](file:///c:/Akakiy%20agent/tools/git.py): Набор инструментов управления версиями Git (`git_status`, `git_diff`, `git_commit`, `git_log`, `git_push`).
* [tools/analysis.py](file:///c:/Akakiy%20agent/tools/analysis.py): Статический AST-анализ структуры файлов (`analyze_file`).
* [tools/validation.py](file:///c:/Akakiy%20agent/tools/validation.py): Проверка синтаксиса Python-файлов проекта (`validate_project`).

### Принципы развития кода Акакия
* Не дублируй логику: если инструмент или метод уже есть в `tools/`, используй и расширяй его, а не пиши параллельную реализацию.
* Все новые инструменты обязаны регистрироваться в [tools/registry.py](file:///c:/Akakiy%20agent/tools/registry.py).
* Сохраняй контракт возврата значений инструментами (словари со статусами или кортежи `(result, error)`).

## Уровень 3. 🤖 Мета-правила поведения ИИ-ассистента (Самоконтроль)

### 1. Рабочий цикл разработки: RESEARCH → PLAN → IMPLEMENT → VERIFY
Любая задача выполняется последовательно по четырём фазам:
1. **RESEARCH (Исследование)**:
   * Изучи фактическое состояние файлов на диске, затрагиваемые модули, места вызовов и зависимости.
   * Источник истины — только диск. Никогда не полагайся на память предыдущих диалогов или устаревшие описания.
2. **PLAN (Планирование)**:
   * Для нетривиальных задач перед внесением изменений определи список файлов, конкретные функции и суть планируемых правок до начала реализации.
   * Для простых локальных задач этот этап может быть кратким и объединён с фазой RESEARCH.
3. **IMPLEMENT (Реализация)**:
   * Внеси минимальные точечные изменения строго в рамках согласованного плана.
   * Не затрагивай несвязанный код и не делай попутных изменений.
4. **VERIFY (Проверка)**:
   * Проверь синтаксис (через `python -m py_compile` или вызов валидации), тесты и фактический результат.
   * Никогда не объявляй задачу выполненной без прохождения этой фазы.

### 2. Матрица автономности ИИ-ассистента
* 🟢 **Автономно (Действуй самостоятельно)**:
  Чтение файлов, поиск по проекту, статический анализ, проверка синтаксиса, запуск тестов, исполнение консольных команд для исследования и верификации, локальные точечные исправления строго в рамках поставленной задачи.
* 🟡 **Объяснить и выполнить (Сначала кратко поясни намерение)**:
  Изменение публичных сигнатур функций, изменение формата возвращаемых контрактов, правки в нескольких взаимосвязанных модулях, нетривиальный рефакторинг в границах задачи.
* 🔴 **Остановиться и спросить (Требует явного одобрения пользователя)**:
  Архитектурные изменения, удаление файлов/классов, удаление существующей функциональности, любые операции изменения состояния Git, потенциально опасные или разрушительные системные команды.

### 3. Регламент работы с Git
* **Read-only операции (разрешены для анализа и проверки)**:
  Команды `git status`, `git diff`, `git log` разрешено выполнять автономно для проверки состояния рабочей копии, контроля диффов и формирования отчётов.
* **State-mutating операции (строго по прямому указанию пользователя)**:
  Команды `git add`, `git commit`, `git reset`, `git restore`, `git checkout` и любые другие операции, изменяющие состояние репозитория, выполняются **исключительно по прямому указанию пользователя**.
* **Выгрузка в удалённый репозиторий (`git push`)**:
  Категорически запрещена автоматическая или фоновая выгрузка. Команда `git push` требует **отдельного явного подтверждения пользователя непосредственно перед выполнением**.

### 4. Регламент выполнения консольных и терминальных команд
* **Разрешено автономно (без дополнительного согласования)**:
  Консольные команды, необходимые для исследования, разработки и проверки проекта, выполняются ассистентом самостоятельно:
  * Исполнение PowerShell-команд;
  * Запуск Python и скриптов в виртуальном окружении (`.\.venv\Scripts\python.exe`);
  * Синтаксическая компиляция (`py_compile`);
  * Запуск тестов, локальных проверок и отдельных вспомогательных скриптов;
  * Чтение файлов через консоль, поиск файлов и текстовых фрагментов;
  * Анализ структуры проекта;
  * Запуск команд, необходимых для проверки фактического поведения изменённого кода.
  > Не нужно каждый раз запрашивать разрешение на такие команды.

* **Ограничения и правила безопасности**:
  * **Scope команды**: консольные команды не должны использоваться для внесения изменений за пределами текущей задачи.
  * **Запрет на деструктивные действия**: запрещено выполнять потенциально опасные или разрушительные команды (`Remove-Item`, массовое удаление файлов, полная очистка проекта, правка системных настроек) без отдельного согласования.
  * **Оценка риска**: если команда может привести к потере данных или необратимому изменению проекта — остановись и запроси подтверждение.
  * **Приоритет правил Git**: консольные команды терминала не могут использоваться для обхода ограничений Git (`git commit`, `git push` и др. подчиняются разделу 3).
